#### 集群刷新

刷新 FreeBSD.org 集群机器上运行的软件的工作仍在继续。我们已开始在 stable/15 上运行生产工作负载。作为此项工作的一部分，一些工作负载被迁移到不同的机器上。此项工作在本季度末仍在进行中。

集群管理团队以大约每六到八周的周期刷新生产软件包构建器（约 35 台物理机器）。这些机器运行着 FreeBSD current 快照。

其他机器根据需要升级，根据其暴露程度跟进安全修复。

截至撰写本文时，集群中有 142 台物理机器。其中 42 台运行着 current，21 台运行着 stable/15，73 台运行着 stable/14。

剩余的 stable/13 安装大部分将升级到 stable/15。

FreeBSD 项目的基础设施持续受到爬虫的攻击，这些爬虫收集用于大语言模型（“AI”）的训练数据。训练这些模型的公司已将爬取操作从其自身易于识别的基础设施大量转移到僵尸网络（“住宅代理”），使其难以在网络边缘阻止而不造成显著的附带损害。本季度集群管理团队再次花费大量时间缓解这些分布式拒绝服务攻击。

### Bug 分拣团队

**链接**：

[FreeBSD Bugzilla](https://bugs.freebsd.org/)

[随时间变化的未解决问题总数](https://bugs.freebsd.org/bugzilla/page.cgi?id=showreport.html&type=total_open_bugs_over_time)

**联系方式**：Bug 分拣团队 <[bugmeister@FreeBSD.org](mailto:bugmeister@FreeBSD.org)>

本季度我们减少了问题报告的数量。

虽然我们确实继续收到了 src 树的补丁，但收到的大部分补丁是针对 ports 的。这可能是由于我们实施的自动通知程序定制。

对于 src 树，在过去 180 天中我们收到了 643 份新问题报告并关闭了 844 份。对于 ports，这两个数字分别为 3493 和 4375。

我们目前没有统计其中实际有多少产生了提交，尽管我们相信数量不可忽视。

在同一 180 天期间，Mark Linimon 和 Torsten Zuehlsdorff 继续分类较早的问题报告。Mark 的工作在 2025 年部分由 FreeBSD 基金会资助。这些结果可以从我们的[随时间变化的未解决问题总数](https://bugs.freebsd.org/bugzilla/page.cgi?id=showreport.html&type=total_open_bugs_over_time)图表中最后两次下降中看到。

此外，今年我们似乎得到了各 FreeBSD 提交者更多的关注。如果你有兴趣提供帮助，请联系 [bugmeister](mailto:bugmeister@FreeBSD.org)。

当然，我们在分类 PR 方面仍然比引起对已有 PR 的关注做得更好。欢迎提供建议。

Mark Linimon 承担了一项长期项目，确保所有提交的补丁都能应用。然而，他不自称是 QA 人员，无法自行评估补丁的适用性。

总体结论是，随着用户教育，今年我们收到了质量更高的问题报告。特别是，带补丁的报告在到达后一两周内就会测试适用性，并在需要时进行修正。

然而，时间越往前追溯，PR 的问题就越大，尤其是 2019 年及更早的。我想这是意料之中的。Mark 继续在后台处理这些。当前计数为 2611。其中约 427 份（主要来自 2019 年及更早）仍需进一步工作。

修复了升级到 Bugzilla 5.2 的设置问题。在轻量级测试中未发现明显的回归。向 5.2.1 的错误修复版本即将推出。计划在其发布后，尽快进行切换到该代码库。最初计划地更早，但在 FreeBSD 15.0 发行工程进行期间似乎不可取，后来又因 15.1 而进一步推迟。

`patchQA.py` 仍处于测试阶段。补丁应用代码无法胜任其任务，必须替换。

`patchQA.py` 的另一个已知问题是，它不知道由 `installworld` 安装到 **/etc** 的文件的来源。有一些外部 shell 脚本正在测试中，可帮助自动修复数据。这可能比为该目的编写更多脆弱的 Python 代码更简单。

我们根据用户请求创建了许多新的 Bugzilla 账户。今年新账户请求数量有所增加。截至 2026 年目前我们达到 291 个，差不多每天 2 个。

距离我们开始要求通过电子邮件请求创建账户而非允许自动请求已有一年。通过这样做，垃圾信息泛滥减少到几乎为零。

我们正在监控的另一个问题是来自爬虫的大量 http 请求。目前这些请求的数量远远超过实际 FreeBSD 用户的请求。这些是用户抱怨的突然变慢的原因。由于我们都不是专业系统管理员，我们欢迎有处理此类问题专业经验的人提供帮助。

感谢 Alexander Ziaee 和许多其他帮助我们达到当前状态的人。

### bhyve 的完整 CPUID 控制

**联系方式**：Hans Rosenfeld <[rosenfeld@grumpf.hope-2000.org](mailto:rosenfeld@grumpf.hope-2000.org)>

#### 项目概述

此项目正在将现有的概念验证集成到 FreeBSD 中，并添加以下可用性功能：

* 一种用户友好的配置方法，用于按需覆盖单个位、部分甚至整个 CPUID 函数，同时保留其余主机 CPUID 信息或预定义的 CPUID 配置
* 一种用户友好的配置方法，用于配置 bhyve 报告的虚拟机监控器签名
* 一组基于常见 x86 架构级别的预定义 CPUID 配置，可能还包括一些真实 CPU 型号的 CPUID 数据，以及一种用户友好的配置方法来为配置虚拟机进行选择

#### 上季度的变更

##### 扩展 bhyve 配置语法

现有的 bhyve 配置文件语法仅限于对配置节点的赋值，在内部解析为树结构的 nvlist 集合。

为了使用预定义配置文件片段进行更灵活的配置，bhyve 配置文件语法新增了两项新功能：

* 可以使用 `+=` 运算符向配置节点追加内容。如果已将值分配给同一配置节点，则新值将追加到旧值之后，以逗号分隔。
* 可以使用 `include` 指令包含另一个配置文件。支持绝对和相对路径，但相对路径理解为相对于包含 include 指令的配置文件所在路径。

##### 更灵活的 CPUID 配置

CPUID 配置机制扩展以支持符号功能名称，其中每个名称对应 CPUID 函数寄存器中的特定位。这对于可以随意关闭或开启的单个指令集扩展或其他可选功能特别有用。

因此，不再需要配置 `cpuid.0x00000001+=edx|=0x00040000`，你现在只需写 `cpuid.enable+=psn`。还有一个用于符号功能的相应选项 `cpuid.disable`。

当然，CPUID 寄存器上的位操作仍然受支持，因为并非所有 CPUID 功能都能以单个功能位表示。

##### 使用 x86 架构级别

x86 架构级别现在实现为一组预定义配置文件片段，每个更高级别在较低级别之上构建。

为了说明这一点，以下是 **x86-64-v3.cfg** 现在的样子：

```ini
include x86-64-v2.cfg
cpuid.enable+=fma,movbe,osxsave,avx,f16c
cpuid.enable+=bmi1,avx2,bmi2
cpuid.enable+=abm
```

CPU 或架构模型可以通过在 bhyve 配置文件中从 **/usr/share/bhyve/cpu** 包含相应的配置文件来选择，也可以在命令行上作为 vCPU 配置的一部分指定：`bhyve [...] -c 16,model=x86-64-v1 [...]`

##### CPUID 约束

为了防止意外为客户 CPU 启用主机 CPU 不支持的 CPUID 功能，CPUID 配置解析器扩展了 CPUID 约束列表，在设置或修改特定 CPUID 寄存器值时会参考这些约束。

对于 CPUID 函数中的任何寄存器，约束可以指定位哪些是不可变的，哪些只能清除。

约束在应用 CPUID 配置后检查。

#### 下季度计划

* 实现 CPUID 约束的覆盖，以忽略任何约束或在违反约束时发出警告而非使虚拟机设置失败。
* 提供更多基于真实 CPU 的预定义 CPU 配置。
* 类似于设置 x86 架构级别，将实现一种机制来覆盖虚拟机监控器标识，而无需手动更改 CPUID 位。
* 审查整个代码集，接受后提交到 FreeBSD。

### Sylve——FreeBSD 统一系统管理平台

**链接**：

[网站](https://sylve.io)

[GitHub](https://github.com/AlchemillaHQ/Sylve)

[CI](https://sylve-ci.alchemilla.io)

[Discord](https://discord.gg/bJB826JvXK)

**联系方式**：Hayzam Sherif <[hayzam@alchemilla.io](mailto:hayzam@alchemilla.io)>

Sylve 是一款面向 FreeBSD 的现代化统一系统管理平台。它提供集成的 Web 界面，用于管理虚拟机（通过 bhyve）、Jail、其周围的网络以及 ZFS 存储。

后端使用 Go 实现，前端使用 Svelte 构建。该项目强调最小的系统占用。默认情况下，它不需要基本系统之外的任何软件包。

可选的运行时依赖项，仅在使用其各自功能时才需要，包括：

* [devel/libvirt](https://cgit.freebsd.org/ports/tree/devel/libvirt/) 用于虚拟化
* [devel/qemu-tools](https://cgit.freebsd.org/ports/tree/devel/qemu/) 用于磁盘镜像管理
* [net/samba419](https://cgit.freebsd.org/ports/tree/net/samba419/) 用于 SMB 文件共享
* [sysutils/swtpm](https://cgit.freebsd.org/ports/tree/sysutils/swtpm/) 用于 TPM 仿真支持
* [dns/dnsmasq](https://cgit.freebsd.org/ports/tree/dns/dnsmasq/) 用于 DHCP 和 DNS 服务

该 Port 为方便用户引入了这些依赖项，但 Sylve 本身不需要任何依赖项即可运行。

#### 第二季度进度亮点

##### 数据中心/集群

* 实现了让用户拥有高可用虚拟机和 Jail 的方式，在 ZFS 复制的帮助下自动故障转移到集群中的次要/三级等节点（尚不支持实时迁移）。
* 可以在没有 Quorum 或 HA 的集群中轻松迁移虚拟机/Jail，UI 中有一个简单的“迁移”按钮。
* 备份和恢复工作流得到显著改进，增强了错误处理和更好的用户反馈，包括对加密数据集的支持。

##### 网络

* 添加了从 Web UI 添加网络路由的支持。
* 现在实现了基于 PF 的防火墙，全面支持流量和 NAT 规则，包括在规则中使用对象来表示 IP 列表、FQDN 等。
* 添加了直观的 WireGuard 配置 UI，允许用户轻松设置和管理 WireGuard 隧道。

##### 存储

* [smart(8)](https://man.freebsd.org/cgi/man.cgi?query=smart&sektion=8&format=html) 作为依赖项引入，作为 smartmontools 的替代方案
* ZFS 存储池管理现在支持创建特殊 VDEV。
* Samba 现在使用内置的 mDNS 服务器而非 avahi
* 添加了初始 iSCSI 支持，允许用户直接从 Web UI 创建和管理 iSCSI 目标和发起程序。

##### 虚拟机和 Jail

* UI 响应速度和性能得到改进，特别是对于具有许多虚拟机/Jail 的大型集群。
* 添加了对 Jail 直接进行 VLAN 标记的支持，而不需要用户为每个 VLAN 创建单独的网桥。
* 许多手动命令行标志现在转换为虚拟机的 libvirt XML 语法，使管理更容易并与基于 libvirt 的工具更好兼容。
* 大幅改进了虚拟机和 Jail 的自动启动/停止流程。

##### 通用

* 通知系统经过重新设计，添加了对 discord webhooks、ntfy.sh 和基于 SMTP 的传输的支持，现在还支持同时使用多种传输方式，并允许用户配置他们想要接收通知的事件。

#### 路线图更新

* 上一季度路线图中的所有项目（NFS 共享除外）均已完成，我们正在开发第三季度的新功能集：
  * NFS 共享支持，用户可直接从 Web UI 创建和管理 NFS 共享。
  * 简化的 UI 模式，旨在让新用户更容易开始将 Sylve 作为 NAS 设备使用。
  * Podman 和 OCI 容器支持，用户可在虚拟机和（经典）Jail 旁运行容器。
  * iOS 和 Android 移动应用程序，用户可随时随地管理其集群。
  * 应用模板库，用户可一键部署流行应用程序（如 Nextcloud、Plex 等）。

### 进程描述符 API 完成 2

**联系方式**：Konstantin Belousov <[kib@FreeBSD.org](mailto:kib@FreeBSD.org)>

**链接**：

[sys: add pdopenpid(2)](https://reviews.freebsd.org/D57124)

[pddupfd(2)](https://reviews.freebsd.org/D57163)

在添加了系统调用 [pdwait(2)](https://man.freebsd.org/cgi/man.cgi?query=pdwait&sektion=2&format=html) 和 [pdrfork(2)](https://man.freebsd.org/cgi/man.cgi?query=pdrfork&sektion=2&format=html) 之后，我研究了应用程序程序员请求的其他缺失功能。需求最大的功能似乎是获取现有进程的进程描述符。

目前只有一个文件描述符可以引用内核中的内部 struct procdesc，这部分解释了为什么通过 pid 打开进程的接口尚未完成。此项工作使 procdesc 可以被多个文件指向。控制 procdesc 行为的属性（例如 daemon——关闭文件不终止进程）从 procdesc 移到了文件。

此更改允许扩展 procdesc 内部接口以实现系统调用 [pdopenid(2)](https://man.freebsd.org/cgi/man.cgi?query=pdopenid&sektion=2&format=html)。

Linux pidfd 描述符实现的一项功能是系统调用 `pidfd_getfd()`，它将指定的文件描述符从目标进程复制到调用者。FreeBSD 的实现名为 [pddupfd(2)](https://man.freebsd.org/cgi/man.cgi?query=pddupfd&sektion=2&format=html)，在有了 `fget_remote(9)` 辅助函数之后，实现就相对简单了。

在开发检查允许操作所需权限的算法时出现了一个问题。内核检查 `p_candebug()` 的结果以查看是否应允许直接访问远程进程的编程资源。但 `p_candebug()` 的结果仅在持有目标进程锁时有效。此外，如果目标进程通过 [execve(2)](https://man.freebsd.org/cgi/man.cgi?query=execve&sektion=2&format=html) 更改执行程序，`p_candebug()` 会拒绝操作，因为如果映像是 set-uid 或 set-gid 的，可能会更改进程的权限。总体而言，使用 `p_candebug()` 的简单检查不够充分，因为我们无法在 `fget_remote()` 期间持有进程锁。

为此，开发了一种机制，为目标进程中的 exec 与调用者之间提供互斥，称为 execblock。还添加了引用进程当前 vmspace 的辅助函数，以避免在操作仅需要一致的目标地址空间时（如读取进程字符串或复制进程内存）使用 execblock。识别了系统中受此竞态影响的现有位置，并根据需要应用了 execblock 或 vmspace 引用接口。

然后，借助 `fget_remote()` 和 execblock 实现了 [pddupfd(2)](https://man.freebsd.org/cgi/man.cgi?query=pddupfd&sektion=2&format=html)。

此项工作旨在让 FreeBSD 支持休眠（挂起到磁盘），无需 BIOS/固件协助即可保存当前机器状态，适用于 `amd64` UEFI 引导的机器。另请参阅[上一份报告](https://www.freebsd.org/status/report-2026-01-2026-03/#_hibernate_aka_suspend_to_disk)。

在近两个月的暂停后，我们修复了映像保存原型中的一些错误，将其 rebase 到最近的代码上，并修改了内核和恢复 EFI 加载器之间的接口，双方都需要做一些修改。这导致了 ACPI 通用挂起/恢复代码中的一些更改和顺带的修复。EFI 加载器（阶段 1）的工作正在进行中。内核恢复部分（阶段 2）的草稿设计完成。

进一步讨论了如何在保持一致性的同时保存系统映像，因为转储操作本身会修改内核内存。目标是确定哪些组件可能干扰转储，以及如何防止这种干扰。特别是，底层 DMA 和 IOMMU 代码在某些情况下可能执行内存分配，目前尚不清楚这是否会在转储期间发生。一旦确定，我们将尽可能消除这些情况，否则将致力于开发类似快照的机制。除此之外，实时快照机制可能是有益的，因为它允许使用任何内核设施来执行转储而不受限制，特别是免除了每个磁盘驱动程序各自实现转储例程的需要。

我们在 6 月的 BSDCan 上展示了此项工作的当前状态、相关挑战和类似快照机制的可能实现，并将在 9 月的 EuroBSDCon 上再次展示。

#### 15.1-RELEASE

由于现实生活原因，我原本希望纳入 15.1-RELEASE 的一些更改最终未能实现（见下文）。最后我只更新了随附驱动程序的手册页。我们还更新了固件 Port，因为 src.git main 中的更改阻止了它们构建。同时 [fwget(8)](https://man.freebsd.org/cgi/man.cgi?query=fwget&sektion=8&format=html) 也更新了更多 PCI ID。最后，我帮助确保已经准备得非常出色的发行说明中添加了一些关于已知问题的额外说明。

#### 更新驱动程序

所有基于 LinuxKPI 的无线驱动程序更新至 main 和 stable/15 中的 Linux v7.0。这最初不在计划中，但事实证明改动很少，所以可以在一个工作日内完成。更新包括

* 已发布的驱动程序 Intel [iwlwifi(4)](https://man.freebsd.org/cgi/man.cgi?query=iwlwifi&sektion=4&format=html) mvm/mld、Realtek [rtw88(4)](https://man.freebsd.org/cgi/man.cgi?query=rtw88&sektion=4&format=html) 和 [rtw89(4)](https://man.freebsd.org/cgi/man.cgi?query=rtw89&sektion=4&format=html)，
* MediaTek mt76 驱动程序（正在进行中），
* 三种 Qualcomm Atheros 驱动程序 ath10k、ath11k 和 ath12k（待办），
* 以及 Broadcom brcmfmac，它可以编译和加载固件但缺少 cfg80211 兼容垫片和一些 netdev 工作。

#### 基于 LinuxKPI 的 802.11 挂起和恢复

随着 drm-kmod 6.12 使我的一台笔记本电脑挂起和恢复，我终于能够调试 LinuxKPI 802.11 挂起和恢复的最后细节，我很高兴地宣布 [iwlwifi(4)](https://man.freebsd.org/cgi/man.cgi?query=iwlwifi&sektion=4&format=html) 的自动挂起和恢复在 main 和 stable/15 中实现。到目前为止，反馈非常积极。遗憾的是，我错过了 15.1-RELEASE 的截止日期，所以请使用 stable 或等待 12 月。

#### LinuxKPI 802.11 调整

作为 Realtek 和 MediaTek 的基础工作，改进了各种 LinuxKPI 802.11 实现细节：

* 重构 chandef/chanctx：这些是关于我们在哪个信道上操作的定义。重构 chandef 仿真以及上下文如何更新；为多个 chanctx 做准备等。
* TX 硬件加密：mt7921 能正常使用软件加密，但一旦启用硬件加密卸载，我们只会收到一些数据包但不再 TX 任何正确的帧。事实证明，根据密钥类型，驱动程序会使用不同的路径访问密钥，而我们以相同方式设置两个密钥，实质上用第二个覆盖第一个。修复了在 set key 调用中传递的参数以避免此问题。这也可能有助于 rtw8x，我们之前在那里看到过与 MC 数据包相关的偶发问题，但验证仍在进行中。
* 速率：开始填写和更新大部分 LinuxKPI 802.11 速率字段（除了一个只有 mt7615 需要的）。此项工作的一部分最初是去年年底为 rtw8x 做的，其中很多是为 MediaTek 补充的。
* 修复了兼容性排序问题：事实证明，我们实现的某些事件顺序并不完全匹配某些驱动程序的期望。当我们从 net80211 到 LinuxKPI 802.11 到驱动程序进行设置和同步各种速率相关部分时，一次更新来得太晚，使 mt7921 只有基本速率。简单地将代码移到不同的顺序调用就解决了问题，使我们获得 11n 和 11ac 吞吐量。

#### LinuxKPI 更改

除了 LinuxKPI 中的 802.11 部分外，还有通用 LinuxKPI 基础设施需要调整。

* PAGE_IS_LKPI_PAGE：该项目旨在将早期的快捷方式（Linux struct page 与原生 vm_page 1:1 映射）转换为具有 vm_page 支持的正确 Linux struct page。这主要是某些 MediaTek mt76 驱动程序需要的，但 drm-kmod 也可以在此落地后最终撤销一些 FreeBSD 特定的变通方法。
* LinuxKPI PCI detach（清理）函数：MediaTek 驱动程序在卸载或关闭时会导致内核崩溃。事实证明，各种 LinuxKPI PCI 清理例程并不完全正确，正如某注释此前已暗示的那样。我们修复了此问题并清理了部分文件。截至撰写本文时，审查仍在进行中，但我们希望至少将关键部分尽快提交。
* LinuxKPI IDR 代码由某些 MediaTek mt76 驱动程序使用，但也与 drm-kmod 和一些半原生驱动程序共享。遗憾的是，该框架有已知问题（如一些历史所示），并且不再匹配当前期望。由于影响较大，重写有些棘手，但我们希望在 26Q3 初准备好。
* 改进和添加了一些 [lindebugfs(4)](https://man.freebsd.org/cgi/man.cgi?query=lindebugfs&sektion=4&format=html) 代码，以便能够将 debugfs 用于 mt7921 调试。

#### Realtek rtw8x 支持

更新到 Linux v7.0 后，我们之前在某些芯片组上无法关联的问题增加了。[rtw88(4)](https://man.freebsd.org/cgi/man.cgi?query=rtw88&sektion=4&format=html) 和 [rtw89(4)](https://man.freebsd.org/cgi/man.cgi?query=rtw89&sektion=4&format=html) 现在都显示各种问题。还发现了另一个问题，即至少一个芯片组的 [rtw88(4)](https://man.freebsd.org/cgi/man.cgi?query=rtw88&sektion=4&format=html) 驱动程序会停顿 6 秒，实质上让认证超时。目前尚不清楚在什么情况下不会发生这种情况，因为在 Linux 下似乎明显没有这种问题。遗憾的是，未能及时为 15.1-RELEASE 调试此问题。我们希望在第三季度初研究此问题，以评估是否能在 15.0 到达 EOL 之前发布 EN 并修复回归。

#### MediaTek mt76 支持

支持多个 MediaTek mt76 驱动程序的工作正在进行中，主要是 mt7921 和 mt7925。在几项 LinuxKPI 和 LinuxKPI 802.11 改进之后，我可以说 mt7921 在初步版本中以可接受的吞吐量传递数据包。mt7925 同样如此，但至少悬而未决的 LinuxKPI IDR 工作导致了不稳定。mt7915 同样需要 IDR，但也似乎不支持硬件扫描分载，这意味着我们必须彻底修复软件扫描，这同样会帮助 rtw8x——在硬件扫描不可用时它们有奇怪的软件扫描回退。在这些落地并在 main 中完全启用之后，将进一步测试其他芯片组。

除了 LinuxKPI 工作外，我们调试了一个由驱动程序触发的 panic。事实证明，驱动程序在 detach（关闭）期间会重新调度一些工作，然后释放底层内存。这留下了一个已调度的 callout，如果我们尝试遍历 callout 列表，就会导致 panic。

#### LinuxKPI USB 支持

在第一季度我们报告了此问题的阻碍。我很高兴地宣布，解决了一半的阻碍，即我原本想添加的编译器选项现在已从 main 和 stable/15 的源代码树中完全移除。LLVM 现在有一个更新的选项，它只是有问题的原始选项允许内容的子集，在一两年后新的 LLVM 发布版和 GCC 随附时迁移到它会很好。现在剩下的工作是为它重新引入一个最小化的解决方案，而不是将其分散到整个内核或大量单独文件中。有希望在 26Q3 期间的某个时候解决。

### 蓝牙 HID 驱动程序

**链接**：

[FreeBSD wiki 项目页面](https://wiki.freebsd.org/SummerOfCode2026Projects/BluetoothSupportForHIDDevices)

[项目 GitHub 仓库](https://github.com/majintosh/freebsd-bthid)

**联系方式**：Majed Alkhaleefah <[majed@FreeBSD.org](mailto:majed@FreeBSD.org)>

作为编程之夏 2026 的一部分，我一直在开发两个驱动程序，以为蓝牙设备启用 HID 驱动程序支持。

该项目的主要目标是通过两个新驱动程序 `bthidbus` 和 `bthid` 将连接的蓝牙 HID 设备注册为 Newbus 设备。`bthidbus` 充当管理 `bthid` 子设备创建和附加的父总线。`bthid` 充当传输层，生成 `hidbus` 设备并在剥离头后将所有接收到的数据包路由到它。这里的短期目标是启用对无线 HID 连接的支持。长期目标是开始奠定基础，使其他人能够为只能通过蓝牙连接的设备编写驱动程序。

已完成的工作：

* `bthidbus` 可以通过套接字成功打开与蓝牙设备的连接。
* `bthid` 可以接收和管理通过 ivars 从 `bthidbus` 传递下来的套接字。
* `bthid` 可以将报告描述符发送到 `hidbus`，后者成功生成正确的 HID 设备和驱动程序。（例如，通过蓝牙连接的游戏手柄生成 `hgame` 设备和 `evdev` 节点。）
* `hidbus` 和 `evdev` 成功接收蓝牙设备的输入。

当前问题和计划更改：

* 实际的报告描述符、蓝牙地址等必须硬编码到 `bthidbus` 中。我最初考虑将查询/监听逻辑添加到 `bthidbus` 让它充当伪服务器，但我担心这会导致臃肿和范围蔓延。我将采用的方法是依赖 `bthidd` 守护程序的现有查询逻辑，并让它通过 `ioctl` 将新连接信息发送到 `bthidbus`。这将移除 `bthidbus` 当前作为连接发起者的角色，而是仅管理已打开的连接。
* 通过 `evtest` 监控时存在显著的输入延迟。我有两个不同的工作假设。第一个是问题在于 `bthid` 以及它如何通过 taskqueue 管理中断。第二个是问题在于网络协议栈，因为蓝牙数据包在 `bthid` 接收之前通过多个不同的 Netgraph 节点管道传输。这也可能是 `evtest` 的问题；我仍需调查此事。

到目前为止，所有测试都是使用 Nintendo Switch Pro Controller 完成的。

### FreeBSD 上的 ROCm 支持

**链接**：

[带有部分 amdkfd 支持的 drm-kmod fork](https://github.com/Yohello1/drm-kmod-rocm/tree/super-special)

[带有 FreeBSD 修复的 rocm-systems fork](https://github.com/Yohello1/rocm-systems)

**联系方式**：Sourojeet Adhikari <[siri@racha.ca](mailto:siri@racha.ca)>

ROCm 是 AMD 用于其 GPU 的计算平台。目前，FreeBSD 完全不支持 ROCm，无论是在工具链层面还是驱动程序层面。我正在努力改变这一点并将所需更改回溯上游。

据我所知，在 FreeBSD 上有几种方法可以在 GPU 上运行计算负载（如 AI/ML、图形等）；据我所知，这些方法是 Vulkan 和 OpenGL。Vulkan 和 OpenGL 都非常适合计算工作负载，即图形和有时机器学习负载。但有时有些任务不太适合 Vulkan 和 OpenGL，而是在 ROCm/CUDA 中完成，因为 ROCm 和 CUDA 给开发者更多关于任务完成方式的控制。因此我正在尝试将 ROCm 支持引入 FreeBSD，以便我们可以在 FreeBSD 上运行 ROCm 代码/程序。要让 ROCm 工作需要几件事。首先是 AMD 的 LLVM fork，我修补了它、让其能工作并上游化了补丁。接下来是 ROCm 运行时，已修补，我目前正将补丁上游化。最后是 amdkfd 驱动程序，我正在修补，并将一些 LinuxKPI 相关的补丁上游回 FreeBSD 内核。

最近，我向 AMD 的 LLVM fork 上游了更改，以在 FreeBSD 上编译其 fork，这样你就可以构建其 ROCm 工具链。除此之外，我一直在将一系列补丁纳入 LinuxKPI，以缓慢引入 amdkfd 支持。

本项目的目标是改进对 FreeBSD/amd64 和 FreeBSD/arm64 的 OpenJDK 支持。

Java 是许多高性能、关键企业系统的重要运行时环境。确保基于 Java 的应用程序在 FreeBSD 上正确高效运行对于确保 FreeBSD 继续成为企业和各种规模企业及组织的可行且有吸引力的平台非常重要。

本季度大部分时间用于让上游化流程正确启动。我们向 GitHub 上 OpenJDK 组织下的[单独仓库](https://github.com/openjdk/bsd-port)提交补丁，并确保每个 PR 至少由一名上游审查者审查。这样，当我们达到想要将我们的 Port 合并到上游主线的程度时，所有提交应该已经由项目中的某人审查过。

这是一个相当缓慢的过程，因为我们依赖上游审查者的时间。我们还发现，一些在我们的 Port 中经历了很长时间的更改却遭拒绝。然后我们必须重新处理它们，或者如果并非严格需要，就直接丢弃它们。我觉得这是有用的纠正，但有时会导致相当多的工作。

本报告继续 FreeBSD HPC Ports 现代化倡议。前几个季度侧重于使 Slurm + PMIx + PRRTE + UCX 栈保持最新状态，并填补周围生态系统中的空白。本季度的工作集中在三个方面：保持核心调度器和通信库与快速移动的上游发布同步，将维护这些 Port 时积累的 FreeBSD 可移植性修复上游化以使本地补丁集不断缩小，以及为大型 HPC 文件系统上常用的 MPI 并行文件实用程序添加新 Port。

#### 已完成的工作

* 本季度两次更新 [sysutils/slurm-wlm](https://cgit.freebsd.org/ports/tree/sysutils/slurm-wlm/)，从 25.11.4 到 25.11.5，然后从 25.11.5 到 26.05.1，跟踪最新上游发布。
* 修复了 [net/ucx](https://cgit.freebsd.org/ports/tree/net/ucx/) 中若干 FreeBSD 特定的运行时问题：强化了异步线程状态处理，更正了 UCM 重定位处理，修复了 mm 信号套接字绑定，并解决了其他 FreeBSD 运行时可移植性问题。
* 将 [net/ucx](https://cgit.freebsd.org/ports/tree/net/ucx/) 从 1.20.0 更新到 1.20.1，并单独修复了 libucm 早期初始化 panic 以及验证更新时发现的若干 gtest 套件失败。
* 添加了 [sysutils/mpifileutils](https://cgit.freebsd.org/ports/tree/sysutils/mpifileutils/) 作为新 Port，及其依赖栈：[devel/libcircle](https://cgit.freebsd.org/ports/tree/devel/libcircle/)、[devel/lwgrp](https://cgit.freebsd.org/ports/tree/devel/lwgrp/) 和 [devel/dtcmp](https://cgit.freebsd.org/ports/tree/devel/dtcmp/)。这些提供了大型 HPC 文件系统上常用的 MPI 并行文件实用程序（复制、删除、校验和等）。
* 本季度两次更新 [benchmarks/py-reframe-hpc](https://cgit.freebsd.org/ports/tree/benchmarks/py-reframe-hpc/) 以跟踪回归测试框架的上游发布。
* 将“UCS/TYPE: Portability fixes for non-glibc/Clang environments”上游化到 UCX，审查和合并完成。
* 向 UCX 开放了“UCS/SYS: portability fixes for non-Linux platforms”，涵盖主机名缓冲区大小调整、通过 `getifaddrs()`/`AF_LINK` 获取 MAC 地址、共享内存错误报告、基于 `mmap`/`munmap` 的重新分配以及基于 `cpuset_getaffinity()` 的线程亲和性查询；目前正在处理审查反馈。
* 向 mpifileutils 开放了可移植性 PR，为 FreeBSD 和其他非 Linux 构建保护 Linux 专属 API；目前正在审查中。
* 与 SchedMD 合作开发了 Slurm 配置时 `H5PTopen` 探测，用于检测 HDF5 高级库，上游合并完成。

#### 进行中的工作

* 处理开放的 UCX 和 mpifileutils 可移植性拉取请求的审查者反馈，推动其上游合并并进一步减少 FreeBSD Port 的本地补丁集。
* 继续与 SchedMD 合作，将在 FreeBSD 上维护 [sysutils/slurm-wlm](https://cgit.freebsd.org/ports/tree/sysutils/slurm-wlm/) 时发现的其他可移植性修复上游化，包括 BSD 套接字处理改进。
* 评估 `proctrack/freebsd_reaper` Slurm 插件设计，这得益于最近落地的 FreeBSD 内核对在进程信息中公开 reaper 元数据的支持。
* 继续密切跟踪上游 Slurm、UCX 和 PMIx/PRRTE 发布，以最小的本地补丁使 FreeBSD Port 保持最新。

#### 后续计划

* 落地悬而未决的 UCX 和 mpifileutils 上游拉取请求，并继续识别更多可移植性问题以上游化而非本地修补。
* 一旦底层内核接口工作最终完成，原型化并提交 Slurm `proctrack/freebsd_reaper` 插件。
* 继续扩展 FreeBSD Ports 集合中可用的 HPC 软件生态系统，并在可能上游接受的地方减少跨栈的本地补丁集。
* 编写 FreeBSD 上 Slurm + OpenMPI + PMIx + PRRTE + UCX 部署的参考文档，以降低在 HPC 环境中试验 FreeBSD 的新站点的入门门槛。
