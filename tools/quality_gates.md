# 翻译质量门禁与检查清单

本文件是 [AGENTS.md](../AGENTS.md)“标准化翻译流程（S0–S6）”的执行细则，供译者和审校者逐项核对。流程阶段、门禁顺序与提交记录要求见 AGENTS.md；术语以 [glossary.yml](glossary.yml) 为准。两者冲突时以 AGENTS.md 为准。

## 三审三校六轮

- **一审（准确性）**：双语对齐逐句编号，核对信息、数字、版本、日期、链接、专名。通过条件为漏译 0、增译 0、事实偏差 0。
- **二审（汉语表达）**：遮蔽英文冷读，逐句过“主干是什么、修饰语属于谁、删去修饰是否成立”三问；按 E1–E20 与病句 12 条逐条扫描。通过条件为每句一遍读懂，命中项为零。
- **三审（术语与一致性）**：对照 `tools/glossary.yml` 逐节比对，同词同译、同义同词。通过条件为术语偏离 0。
- **一校（事实核验）**：回查原文并联网核验全部版本号、提交统计、评审编号、外链锚点；失效链接与可疑数据需联网复查三次。
- **二校（交叉复核）**：换视角冷读，对前几轮每处修改回读；逐句核对译文与原文的语义对应，禁止抽样。
- **三校（规范终校）**：逐项扫描引号、加粗、反引号、空格、链接区块、联系方式、标题层级、代码块注释，并朗读每段。
- **递归**：六轮后仍有问题，回到一审重新执行，直至完整一轮零发现。每轮只处理新问题，不复查已完成的旧结论。

## 去欧化汉语清单（E1–E20）

- **E1 无必要的“被”字句**：有施动者改主动；无施动者改陈述或用“经”。反例 → 正例：该问题被团队修复 → 团队修复了该问题。
- **E2 长定语套叠**：超过 20 字的定语拆句或后置。反例 → 正例：一个由基金会资助、用于改进音频、覆盖 USB 音频的驱动 → 该驱动由基金会资助，用于改进音频，覆盖 USB 音频。
- **E3 名词化**：“进行/作出/加以 + 名词”还原为动词。反例 → 正例：对代码进行分析 → 分析代码。
- **E4 “对……的支持/实现/改进”**：改为动宾。反例 → 正例：对 ZFS 的支持 → 支持 ZFS。
- **E5 “的”字堆叠**：单句不超过 3 个。反例 → 正例：这是用于验证该功能的新的测试的集合 → 这组新测试用于验证该功能。
- **E6 冗余介词框架**：删“在……方面/对于……来说/关于……”。反例 → 正例：在性能方面有所提升 → 性能有所提升。
- **E7 抽象名词作主语**：换具体主体。反例 → 正例：这项工作的完成标志着…… → 团队完成了这项工作，……。
- **E8 “当……时”“通过……来……”**：改为“……时”“用……”，或直接用动词。反例 → 正例：通过使用 pkg 来安装 → 用 pkg 安装。
- **E9 “使得/使得其”**：改“使”“让”或主谓句。反例 → 正例：这使得其能够运行 → 因此可以运行。
- **E10 偷换主语**：分句主语保持一致，否则补主语或断句。反例 → 正例：该驱动支持 A，并被广泛使用 → 该驱动支持 A，社区广泛使用它。
- **E11 连接词冗余**：“并且/而且/此外”能删则删。反例 → 正例：并且它还修复了…… → 它还修复了……。
- **E12 “了”“着”滥用**：删除无语法作用者。反例 → 正例：增加了对……的支持 → 新增对……的支持。
- **E13 程度副词滥用**：删“非常地/极大地”等空修饰。反例 → 正例：极大地提升了 → 提升了。
- **E14 英文复数硬译**：不加“们”“各种的”。反例 → 正例：各种的驱动程序们 → 各驱动。
- **E15 语序倒置**：恢复话题—说明结构。反例 → 正例：性能的提升由该补丁实现 → 该补丁提升了性能。
- **E16 无依据的“之一”**：仅原文有 `one of` 时保留。反例 → 正例：这是重要项目之一（原文无） → 这是重要项目。
- **E17 后置修饰从句**：拆为独立句或前置短定语。反例 → 正例：该补丁，它修复了崩溃，已被合并 → 该补丁修复了崩溃，现已合并。
- **E18 “关于……的讨论/决定”**：改为动宾或主谓。反例 → 正例：关于预算的讨论正在进行 → 团队正在讨论预算。
- **E19 逻辑连接词滥用**：“因此/从而/进而”仅在确有因果、递进时保留。反例 → 正例：因此从而提升了性能 → 性能因此提升。
- **E20 英文语序的并列堆叠**：按汉语习惯重排或分句。反例 → 正例：支持 A，B，以及 C 的实现 → 实现 A、B 与 C。

## 病句检查表（12 条）

1. 成分残缺：缺主语、宾语或谓语中心语。
2. 搭配不当：动宾、主谓、修饰语与中心语不搭。
3. 语序不当：定语、状语位置错误。
4. 句式杂糅：“原因是……造成的”“本着……为原则”。
5. 关联词缺失或误配：“虽然……但是”“不仅……而且”。
6. 指代不明：“这/该/其/它”存在多个先行词。
7. 重复赘余：“大约 50 左右”“首先第一”。
8. 多重否定导致语义反转。
9. 数量与范围歧义。
10. 逻辑断裂：因果、转折与原文不符。
11. 主宾倒置：动作发出者与承受者颠倒。
12. 时态与完成态误用：把进行中译为已完成，或反之。

## 格式一致性专检（10 维）

格式专检与内容校对分开执行，逐段覆盖全文，不以抽查代替。

1. **标题层级与冒号**：`##`/`###`/`####`/`#####` 层级不跳跃；中文标题用全角冒号；标题不以句号或强调符号结尾；标题内 man 页引用按 AGENTS.md 处理。
2. **链接区块**：多条链接用 `**链接**：` 单独成行，条目各占一行并以空行分隔；单条链接与 `**链接**：` 同行；链接目标与上游一一对应。
3. **联系方式与赞助者**：`**联系方式**：` 加粗、全角冒号、邮箱写成 `<[邮箱](mailto:邮箱)>`；多个联系人各占一行；`**赞助者**：` 与上游 `Sponsor:` 条数一致。
4. **列表标记与嵌套**：列表标记与上游保持一致；嵌套层级与缩进正确；列表前后有空行；同层列表项标点风格统一。
5. **代码块与注释**：语言标记按实际内容选择，禁止 `text`；代码块内英文注释译为中文；代码、命令、路径、引号不得篡改。
6. **引号与全角标点**：正文只用“”与‘’，禁止「」『』与半角引号；中文语境使用全角逗号、分号、冒号、括号；英文专名内部标点保持英文。
7. **CJK 空格**：中文与英文、数字之间加半角空格；中文之间不留多余空格；纯中文加粗前后按 AGENTS.md 规则处理；链接与行间代码两侧按语料先例处理。
8. **路径与 IP 加粗**：正文中的路径与 IP 使用加粗，不用反引号；代码块、行间代码、链接目标中的路径保持原样。
9. **命令与 man 页引用**：带选项或参数的命令用行间代码；裸命令不加包裹；man 页引用用加粗；带链接的 man 页引用保持原样。
10. **段落与空行**：一段一行，段间空行；无软换行、无行尾空白、无多余空行；文件以单个换行结尾。

每处命中须有“规则条 + 全书语料先例 + 上游格式”三方证据。规则与上游或语料冲突时，登记为例外，不擅自扩大改动范围。

## 量化验收指标

- 漏译、增译：0
- 事实偏差：0
- 术语偏离：0
- 标题层级计数偏差：0
- 列表项数偏差：0
- 链接目标遗漏：0
- 邮箱、man 页引用、行间代码、代码行遗漏：0
- 版本号、百分比、日期、提交哈希、评审编号遗漏：0
- 平均句长：≤ 45 字
- 单句超过 80 字占比：≤ 2%（技术枚举句除外）
- 单句“的”数量：≤ 3
- “被”字句密度：≤ 3 处/千字
- “进行/作出/加以”密度：≤ 1 处/千字
- “使得”密度：≤ 1 处/千字
- markdownlint 报错：0
- 不可见字符：0
- 代码块注释未译：0

## 门禁命令

在仓库根目录依次执行，上一项未通过不得继续：

```sh
markdownlint-cli2 "<中文.md>" --config .github/.markdownlint.json
python tools/structure_check.py <中文.md>
python tools/object_check.py <中文.md>
python tools/term_check.py <中文.md>
python tools/text_metrics.py <中文.md>
python tools/invisible_chars.py <年份目录>
python tools/selftest.py
git diff --check
```

- `structure_check.py` 与 `object_check.py` 任一报“上游有、中文无”即阻断。
- `markdownlint-cli2` 报错逐处手工修正，禁止用 `--fix` 批量接受。
- `selftest.py` 用于验证检查器本身；修改 `tools/` 后必须先跑通自测。
- 编码为 UTF-8 无 BOM、换行 LF，由 `.editorconfig`、`.gitattributes` 与 docs-qa 工作流共同保证。

## 门禁记录格式

PR 描述或 PR 评论按以下顺序记录，缺项视为未完成 S6：

- **范围**：报告期、条目数、目标文件、上游快照目录。
- **结构**：二级/三级/四级/五级标题计数，列表项数，链接目标遗漏数。
- **对象**：链接、邮箱、man 页引用、行间代码、代码行、数字对象的“上游数/中文数/遗漏数”。
- **格式**：逐段核查覆盖的条目数，命中数，修正数，例外数。
- **工具**：各命令的退出码或报错数。
- **例外**：规则与上游或语料冲突之处，附三方证据与取舍理由。
- **提交**：commit 哈希与变更文件列表。

## 失效模式与对策

- **以句子级校对替代对象盘点**：属性展开产生的邮箱、链接与格式转换后隐藏的对象会漏检。对策：S3 独立执行 `object_check.py`，六类对象全量比对。
- **以抽样代替全量**：长尾条目和低频对象最容易漏掉。对策：明令禁止抽样，逐句、逐对象覆盖。
- **内容校对与格式检查混在一起**：格式问题在内容轮被当作小节放过。对策：S4 独立门禁，逐段核查 10 个维度。
- **机械套用规则**：把上游的斜体、行间代码、列表标记误改为项目习惯，造成失真。对策：改前核对上游格式与全书语料先例，冲突时登记例外。
- **工具无自测**：检查器本身漏报却给出“通过”。对策：`tools/selftest.py` 与 docs-qa 工作流双重验证。
- **无记录**：无法证明全量覆盖。对策：PR 证据表与评论留痕，记录计数、退出码、哈希。
- **脚本改写正文或残留**：不可审计，且可能引入批量错误。对策：脚本只检测，修改逐处手动；临时脚本放 `script/`，任务结束删除。

## 维护规则

- 上游报告结构或项目规则变化时，先更新本文件，再更新工具与 PR 模板。
- 新增检查项必须同时提供可执行的检测方式或明确的人工判定标准。
- 本文件与 AGENTS.md 冲突时以 AGENTS.md 为准，并在 Issue 中指出冲突。
